2. Domain Event Definition & Publishing

Domain events in Kora represent immutable facts that have occurred in the domain. They reside in the feature's events/ directory:

src/features/orders/events/order_events.kora 
model OrderPlacedEvent {
    order_id: Int,
    customer_id: Int,
    total_amount: Float,
    currency: String,
    timestamp: Int,
}

model OrderCancelledEvent {
    order_id: Int,
    reason: String,
    timestamp: Int,
}
Publishing Event via Event Bus 
class OrderService {
    event_bus: EventBus,

    init(event_bus: EventBus) {
        this.event_bus = event_bus
    }

    fn place_order(order_id: Int, total: Float) -> Bool {
        let event = OrderPlacedEvent {
            order_id: order_id,
            customer_id: 42,
            total_amount: total,
            currency: "USD",
            timestamp: 1731845100,
        }

        // Asynchronously publish to "orders.placed" topic
        this.event_bus.publish("orders.placed", event)
        print("[OrderService] Order placed event dispatched")
        return true
    }
}

3. Distributed SAGA Transactions

In a distributed system, traditional ACID database transactions across multiple databases are impossible or introduce severe performance bottlenecks. Kora implements the SAGA Pattern using compensating transactions:

Step Service Action Compensating Action (on failure)
1 Order Service Create Order (Status: Pending) Cancel Order (Status: Cancelled)
2 Payment Service Authorize & Charge Credit Card Issue Refund to Card
3 Inventory Service Reserve Stock in Warehouse Release Reserved Stock
4 Shipping Service Generate Waybill & Dispatch Void Shipping Label
Event Choreography: Each service listens to the preceding event, executes its local database transaction inside an ACID boundary, and emits a success or failure event. If any step fails, compensating events trigger automatic rollbacks across earlier services.

4. Distributed Tracing & Correlation Headers

Kora services automatically extract and propagate W3C Trace Context and distributed correlation headers:

  • traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
  • x-request-id: Unique end-to-end request identifier across all microservices
  • x-correlation-id: Business transaction trace ID (e.g. checkout workflow)

5. Kubernetes Probes & Production Manifest

Every Kora application generated with kora create my-service --template microservice includes production readiness endpoints:

k8s-deployment.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: kora-order-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: kora-order-service
  template:
    metadata:
      labels:
        app: kora-order-service
    spec:
      containers:
      - name: app
        image: kora-order-service:latest
        ports:
        - containerPort: 7582
        livenessProbe:
          httpGet:
            path: /health
            port: 7582
          initialDelaySeconds: 5
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /health
            port: 7582
          initialDelaySeconds: 3
          periodSeconds: 5
        resources:
          limits:
            cpu: "1"
            memory: "512Mi"
          requests:
            cpu: "100m"
            memory: "64Mi"
